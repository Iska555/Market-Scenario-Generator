# Phase 4 thesis system

The thesis system records the owner's reasoning and subsequent reviews. It has no
price feed, valuation calculator, return forecast, trade execution or accounting.
The owner explicitly authorized this phase on 2026-09-09. Phase 5 remains separate.

## Setup and use

Follow [RESEARCH.md](RESEARCH.md) to configure PostgreSQL, `DATABASE_URL` and an
independent `RESEARCH_API_KEY` of at least 32 characters. Run Alembic `upgrade head`
to apply `20260909_02` after the existing research migration. Start the backend
and frontend, then unlock once through the global Private workspace control. The
same memory-only key opens Thesis and the other private workspaces. Navigation
clears unsaved Thesis inputs and results but preserves the global unlock; lock or
page refresh clears the key and all private browser state. Saved versions and
reviews remain in PostgreSQL. Use HTTPS outside local development.

Select an equity security, create a draft, and record the business quality,
variant perception, earnings drivers, catalysts, risks, bear/base/bull cases and
invalidation evidence. Active theses require all substantive narrative sections.
Saving an edit appends a complete new version; older versions remain readable.
Review a selected saved version with an explicit decision and evidence. The five
behavioral prompts help structure reflection; they never generate a decision.

## Storage and time

`research_theses` gives each thesis a stable UUID linked to a research security.
`research_thesis_revisions` stores complete content and sequential version numbers.
Each version captures ticker and exchange at authoring time; a later security
rename does not rewrite those labels. `research_thesis_reviews` binds each review
to one specific revision of the same thesis through a database foreign key.

Authoring and review timestamps are generated by the server in UTC, not supplied
by the browser. `GET /theses/{id}?as_of=...` selects the latest recorded revision
at or before an inclusive timezone-aware cutoff. This is an authoring history,
not evidence that information was publicly available then. Review timestamps do
not change the thesis version timestamp. The latest revision's `created_at` is
the thesis's effective update time; no mutable `updated_at` field is needed.
Version timestamps advance by at least one microsecond if the server clock
repeats or goes backward; reviews preserve per-thesis chronological ordering too.

PostgreSQL triggers reject updates and deletes of all three tables. Application
routes expose append operations only. Revision creation locks the stable thesis
row and checks `expected_revision`; stale submissions return 409. A unique
constraint independently prevents duplicate revision numbers. Database owners
can disable triggers or alter storage: this is operational immutability, not an
external timestamp attestation or protection against a database administrator.

## Assumptions and validation

- Status is manually selected: `draft`, `active`, `invalidated`, `closed`.
- Horizon is an integer from 1 to 1,200 months; conviction is `low`, `medium`,
  or `high`. Neither is inferred from price performance.
- `target_low` and `target_high` are optional paired positive, ordered per-share
  values in explicit `valuation_currency`. They describe an owner value range,
  not confidence bounds or scenario probabilities.
- `required_return` is an optional annual effective fraction greater than −1:
  `0.08` means 8% per year. It is an owner hurdle, not a computed expected return.
- A review's optional `current_price` is a manually entered positive per-share
  quote in that review's declared currency. No feed freshness or FX equivalence
  is inferred. Review currency may differ from the saved revision's currency.
- `updated_expected_return` is an optional owner-declared annual effective
  fraction greater than −1. The system stores it without estimating or comparing
  it to historical returns, target prices or the required return.
- Prices use exact Decimal storage with at most 30 digits; annual rates permit
  20 digits. Both allow at most 10 decimal places. JSON returns Decimal strings or null. Empty optional
  values remain null; missing information is not silently converted to zero.
- Review decisions are `BUY_MORE`, `HOLD`, `REDUCE`, `EXIT`, `WATCH`. A decision
  records an intention and never creates a trade or changes thesis status.

## Private API

All paths below start with `/api/research` and require `X-Research-Key`.

| Method and path | Result |
|---|---|
| `GET /theses/prompts` | Five reusable behavioral questions |
| `POST /theses` | Create identity and first revision; content plus `security_id` |
| `GET /theses?security_id=...` | List thesis identities with latest versions |
| `GET /theses/{id}?as_of=...` | Latest eligible complete version |
| `POST /theses/{id}/revisions` | Append content with required `expected_revision` |
| `GET /theses/{id}/revisions` | Newest-first complete version history |
| `POST /theses/{id}/reviews` | Append manual review with required `revision_id` |
| `GET /theses/{id}/reviews` | Newest-first review history |

Lists support `limit` (1–100) and nonnegative `offset`. Pagination is live, not a
transactionally frozen snapshot; concurrent additions can shift page boundaries.
Responses include UUIDs, UTC timestamps and the associated version identifiers.
The running `/docs` page gives every typed field. Invalid requests return 422,
missing identities 404, stale revision conflicts 409, wrong keys 401, and missing
configuration or database failures 503. Writes commit before a success response.

## Remaining limits

This is a private single-owner interface using one shared key. It has no distinct
author identities, permission tiers, key management screen, automatic reminders,
saved offline drafts, import/backdating or fundamental-observation snapshots
attached to a thesis. Keep original source references in the narrative where
needed. The key must be re-entered after lock or reload. A network interruption
after a successful write can leave the browser uncertain about the outcome;
inspect saved history before retrying. There is no idempotency token for review
creation. Network/database requests have no application-wide timeout; a stalled
connection can remain busy until the underlying request fails or you disconnect.
Lock clears browser state and ignores late responses, but cannot cancel a
transaction already running on the server. Thesis itself does not calculate an
expected return, create an order or change the ledger.
